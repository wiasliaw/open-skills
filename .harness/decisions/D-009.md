# D-009: use-loop covers change-waits inside one session only

- **Status**: active
- **Date**: 2026-11-10
- **Decision**: The use-loop skill handles one shape of loop: wait until a state differs from a baseline or a predicate becomes true, then hand off. Periodic jobs with no change condition and waits that must outlive the orchestrator session are out of scope; the skill points them to Desktop scheduled tasks, `/loop`, or cloud scheduled tasks.
- **Rationale**: Decided with the project owner in the 2026-11-10 interview. A periodic job without a change condition would hand off every tick and return the orchestrator context cost that the skill exists to remove. Cross-session survival needs a resident process (watcher script, launchd, or a paseo schedule), which the owner excluded for this version. Limiting the shape keeps the plugin free of new scripts and daemons.
- **Rejected alternatives**: a child watcher process spawning `claude -p` workers and reporting over the session inbox socket — needs a new script, and inbound messages to a `bypassPermissions` session are held for approval unless `crossSessionInbound` is set to `accept`. A resident daemon or paseo `create_schedule` — survives the session, which the owner excluded. `CronCreate` in the orchestrator dispatching a subagent per fire — every fire still lands a prompt in the orchestrator.
- **Supersedes**: none
