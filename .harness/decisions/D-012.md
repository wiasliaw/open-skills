# D-012: use-loop journals are session state kept out of version control by default

- **Status**: active
- **Date**: 2026-11-11
- **Decision**: A loop journal is session state, not a deliverable. The orchestrator does not commit it. At the first loop creation in a project, when the resolved loops directory lies inside the repository, the orchestrator appends it to the project's `.git/info/exclude`, the same mechanism `scripts/worktree.mjs` uses for worktree paths. When the project's declared VCS strategy says to commit journals, that declaration wins.
- **Rationale**: The PR #12 review noted that `.project/loops/` was not excluded from version control. A journal records one wait and its handoffs; its durable outcome is whatever the orchestrator did next, which lives in the work-unit state or the code. Committing it would add churn to every project that adopts the skill. `.git/info/exclude` keeps the exclusion local to the clone and leaves tracked files alone, which is the pattern the plugin already uses.
- **Rejected alternatives**: adding `.project/loops/` to the consuming project's `.gitignore` — modifies a tracked file in a project the plugin does not own. Committing journals like work-unit state — work-unit state is the harness's contract record and is reviewed; a journal is a wait log with no review gate.
- **Supersedes**: none
