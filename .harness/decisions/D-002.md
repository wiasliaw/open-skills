# D-002: codewalk resolves git paths dynamically instead of using WOR-31's literal path wording

- **Status**: active
- **Date**: 2026-09-30
- **Decision**: The codewalk skill instructs agents to resolve the ignore file via `git rev-parse --git-path info/exclude` and to anchor the `.codewalk/` tree at `git rev-parse --show-toplevel`, rather than using the WOR-31 spec's literal `.git/info/exclude` path and cwd-relative `.codewalk/` placement. The worktree creation command is spelled out verbatim (`GIT_LFS_SKIP_SMUDGE=1 git -c core.hooksPath=/dev/null worktree add --detach <path> HEAD`).
- **Rationale**: Empirically verified during the WOR-31 review (two independent verifiers, scratch-repo tests): in a linked worktree `.git` is a file, so the literal path fails outright, while the spec itself requires linked-worktree launches to work; a cwd-relative `.codewalk/` created from a subdirectory escapes the toplevel-relative exclude pattern and pollutes `git status`; a bare `git worktree add` runs the `post-checkout` hook, violating the spec's "never execute project code". Dynamic resolution honors the spec's stated intent in every case its literal wording breaks.
- **Rejected alternatives**: Copying the spec's literal `.git/info/exclude` and unanchored paths (fails the spec's own linked-worktree and no-code-execution requirements); describing hooks/LFS suppression in prose without a command (a literal-following agent leaves hooks enabled — demonstrated in testing).
- **Supersedes**: none
