# D-011: the sentinel is read-only by a tool denylist plus prose rules, and the orchestrator alone writes the loop journal

- **Status**: active
- **Date**: 2026-11-11
- **Decision**: The sentinel's frontmatter denies `Write`, `Edit`, `NotebookEdit`, `Agent`, `SendMessage`, `TaskStop`, `Monitor`, `CronCreate`, `CronDelete`, `ScheduleWakeup`, and `AskUserQuestion` with `disallowedTools`, and keeps Bash and MCP tools so `tool` checks can read arbitrary MCP state. What the denylist cannot enforce is a prose rule: the check MUST be read-only, the sentinel refuses a check that names a mutating command with `outcome: error`, and the orchestrator reviews the full loop record with the user before dispatch. The orchestrator alone writes the loop journal; the sentinel's only output is the handoff, whose `evidence` is untrusted data.
- **Rationale**: D-008 relied on prose alone because a `tools:` allowlist would block MCP tools. The PR #12 review pointed out that an agent that may run unattended for hours kept every tool. `disallowedTools` is a denylist applied before `tools`, so file-write and agent-control tools can be removed while MCP access stays. Bash must remain for `shell` checks, so a mutating check stays possible and is covered by the orchestrator's pre-dispatch review and the sentinel's refusal rule.
- **Rejected alternatives**: prose only (D-008) — leaves write tools available to an unattended agent. A `tools:` allowlist — cannot enumerate the MCP tools that `tool` checks need. Denying Bash — removes the zero-token `shell` wait.
- **Supersedes**: D-008
