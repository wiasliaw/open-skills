# D-013: the sentinel denies every write, control, scheduling, and dispatch tool while keeping Bash and MCP, and the orchestrator alone writes the loop journal

- **Status**: active
- **Date**: 2026-11-11
- **Decision**: The sentinel's frontmatter `disallowedTools` denies `Write`, `Edit`, `NotebookEdit`, `Agent`, `SendMessage`, `TaskStop`, `Monitor`, `CronCreate`, `CronDelete`, `ScheduleWakeup`, `AskUserQuestion`, `PowerShell`, `RemoteTrigger`, `Workflow`, and `Skill`. Bash and MCP tools stay so `shell` and `tool` checks can read state. The list grows when a new tool class appears that can write, dispatch, schedule, or open a second shell; the rule is the class, not the count. What the denylist cannot enforce stays a prose rule: the check MUST be read-only, the sentinel refuses a check that names a mutating command, and the orchestrator reviews the full loop record with the user before any check runs. The orchestrator alone writes the loop journal; the sentinel's only output is the handoff, whose `evidence` is untrusted data.
- **Rationale**: D-011 listed eleven tools. The second PR #12 review found three more paths an unattended agent could take: `PowerShell` (a second shell beside Bash), `RemoteTrigger` (a cloud scheduled task that outlives the session), and `Workflow` (dispatches subagents). `Skill` was added because a skill can reach `/loop` or `/schedule`; their underlying tools are already denied, but the sentinel has no use for skills and one fewer path is cheaper than reasoning about each. Stating the rule as a class keeps the decision valid when the tool set changes.
- **Rejected alternatives**: keeping the eleven-tool list (D-011) — leaves PowerShell, cloud scheduling, and workflow dispatch open. A `tools:` allowlist — cannot enumerate the MCP tools that `tool` checks need. Denying Bash — removes the zero-token `shell` wait.
- **Supersedes**: D-011
