# D-004: codewalk reads a HEAD worktree snapshot and cites only tracked code

- **Status**: active
- **Date**: 2026-09-29
- **Decision**: `codewalk` stays interactive only (no orchestrator dispatch); its landed file is a reading record written by the walking session, defaulting to `.codewalk/<topic>.md`. Before the first reply it snapshots HEAD into a temporary `git worktree` outside the repository (`git worktree prune`, remove a stale copy at the same path, `git worktree add --detach <path> HEAD`), reads and cites only inside it, pins the commit from that worktree, shows repo-relative `file:line`, and removes the worktree after landing. The walk therefore describes the last commit; uncommitted changes are excluded. Without git or commits it reads the working tree and records `unknown`. It cites only tracked project code — never gitignored paths or files outside the repository, naming such boundaries in prose. Stops are single stop records captured and verified when read (literal, exactly-once anchors; orientation is stop 1; off-route inserts go right after the current stop). The existing-file prompt applies only to files that existed before the walk. PR walkthrough and refresh modes remain deferred.
- **Rationale**: The repository already states what is project code (tracked files) and what need not be read (`.gitignore`). A worktree at HEAD contains exactly that and cannot change during the walk, so the pin is exact by construction and no working-tree status check or snapshot re-check is needed. A dot directory marks the landed file as tool output, not a project deliverable, and keeps codewalk independent of harness layout (`.harness/` is orchestrator-only; `.project/` is a harness-declared location).
- **Rejected alternatives**: Working-tree reading with a `git status --porcelain --ignored` coverage check and landing-time snapshot re-check (D-003) — more machinery for edge cases the repository already classifies, and still racy while the tree changes. Reading via `git show HEAD:<path>` — avoids a checkout but gives up the file tools' search and read ergonomics. Default landing under `docs/walkthroughs/` — mixes reading records into user-facing docs. Landing under `.harness/` or `.project/` — the former is orchestrator-only long-term memory; the latter is harness-specific.
- **Supersedes**: D-003
