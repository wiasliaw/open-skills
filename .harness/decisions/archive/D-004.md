# D-004: use-worktree is ported to main as a standalone skill that keeps the milestone script and its `.harness/config.json` contract

- **Status**: superseded by D-005
- **Date**: 2026-10-16
- **Decision**: The use-worktree skill is ported from `milestone/graph-engineering` by file-level copy, not by merge or cherry-pick. `scripts/worktree.mjs` and its test suite are copied unchanged, including the `ensure --detach` pin mode that nothing on main calls yet. The skill page and doc drop every graph-engineering concept and do not integrate with harness-flow. The script keeps reading the optional, user-authored `.harness/config.json`. Evals are not ported. `milestone/graph-engineering` is left as-is with no back-sync.
- **Rationale**: The milestone branch rebuilt the plugin around graph engineering (it removed harness-flow, handoff, and `.harness/`), and its use-worktree commits mix unrelated files, so a merge or cherry-pick would carry the graph architecture onto main. The script imports only Node.js built-ins and passes its 31-test suite outside the milestone tree, so it ports without change. Keeping the config path avoids any script change. `.harness/config.json` is an accepted exception to "`.harness/` is written only by the orchestrator at merge moments": it is optional configuration read by a script, not long-term memory. A standalone skill leaves harness-flow's "VCS is not prescribed here" rule intact.
- **Rejected alternatives**: Merge or cherry-pick from the milestone — brings the whole graph architecture, and the relevant commits also add unrelated files. Rewrite the Graph profile as a harness-flow profile (orchestrator provisions a worktree before dispatch) — would make harness-flow prescribe VCS operations and widen the change. Move the config out of `.harness/` — requires changing the script. Port the evals now — deferred by the project owner.
- **Supersedes**: none
