## MODIFIED Requirements

### Requirement: Routing state content

`state.json` SHALL be two-layer. The core contract, present for every unit of every graph because it serves the universal machinery (orchestration, the fallback chain, approvals): the unit's identity (an id matching `^[a-z0-9][a-z0-9-]*$`, generated by the orchestrator at creation; the create gate enforces uniqueness against the work-units location, the archive, and the remote's existing `wu/<id>` branches, and on a collision the orchestrator regenerates with a random suffix; timestamps; and the captured trigger: its source — one of `prompt`, `issue`, `ci-failure`, `maintenance-due` — the original request verbatim, and optionally the existing branch a fix unit targets. The factory does not watch external systems: a CI failure or a conflict arrives as a trigger from outside, from the human or project automation); the current node and the current pipeline position within it; the approved phase (null until the phase-approval human task records it; values from the instantiated `phase` type's vocabulary); the walked-path history (the ordered list of executed node ids, the data source for ruling overrides); the problem tracking when escalation is in flight (problem id, scope, failure signature, consultation count, status); the blocked node when escalation is in flight; failure counters keyed by scope — the scope kinds `<node>.<task>` and `edge:<from>-<to>` are universal, and a `re_entry` rule refines the scope of every task that reads its progress field to `<node>.<task>:<item-id>` while an item is selected, which exists only where the re-entry concept does — the item id names a record of that rule's `items_field`; a failing verdict or counted `goto` traversal increments only the finest applicable scope, and each scope also tracks its signature-independent total; advisor consultations keyed per problem, capped at the graph's declared consultation cap; review verdicts and human decisions, each with evidence references and a folder-relative file pointer to the full record; and the outcome with its reason. Everything else is graph-declared state: a field exists because some task of the graph declares `produces: ["state:<field>"]`, its type resolved from the merged type catalogs by field name (see `type-catalog`), and its applicability derived from the nodes whose pipelines reference the producing task — the field exists only in units whose walked or reachable route includes such a node, and is applicable from that node onward, the same derivation the graph validator uses for guard references. A field SHALL NOT exist in a unit outside its applicability, and only a task whose dispatch carries the `produces` authorization — the task in flight at the recorded pipeline position — may cause the orchestrator to write it. The one bounded exception is re-entry bookkeeping, which the routing machinery performs without a producing task: the selection step of a `re_entry` rule (its progress field takes an element of its list field, which loses that element — the first one under `declared` order) and updates to existing records of its `items_field` (no record added, removed, or reordered; `id` and command-typed fields unchanged — for example the ticket status flip recorded with a green verdict). The plugin's template factories declare the contract reference and the ticket list with its current selection — per ticket only the routing data: id, status, verification command, evidence references; descriptive ticket content lives in the decomposition stage's files. Full content lives in stage files; `state.json` holds verdicts, counts, enums, dates, and pointers.

#### Scenario: Graph-declared routing field
- **WHEN** a task of the graph produces `state:<field>` and the merged catalogs type it
- **THEN** validation SHALL accept that field, with its catalog type and values, in `state.json` for units running that graph

#### Scenario: Unauthorized state write rejected
- **WHEN** a state write for a field arrives from a task whose `produces` does not include it
- **THEN** the write gate SHALL reject the write naming the task and the field

#### Scenario: Re-entry bookkeeping authorized
- **WHEN** a write selects the next pending item of a `re_entry` rule, or changes the status of an existing record of its `items_field`, with no task in flight that produces those fields
- **THEN** the write gate SHALL accept it as re-entry bookkeeping, and SHALL still reject a write that adds, removes, or reorders records or changes a record's `id` or command-typed field without a producing task in flight

#### Scenario: Factory without tickets
- **WHEN** a graph has no task producing ticket fields
- **THEN** its units' `state.json` SHALL contain no ticket fields and no per-item counter scopes, and validation SHALL reject them if present

#### Scenario: Route without tickets
- **WHEN** a unit's route never reaches a node referencing the ticket-producing task, in a graph that does declare tickets
- **THEN** that unit's `state.json` SHALL likewise contain no ticket fields, and validation SHALL reject them if present

#### Scenario: Verdict recorded with pointer
- **WHEN** the orchestrator records a review verdict
- **THEN** the entry SHALL carry at least one evidence reference and a folder-relative pointer to the reviewer's report file

#### Scenario: Counters feed escalation
- **WHEN** a failing verdict is recorded for a scope
- **THEN** the orchestrator SHALL increment that scope's failure counter in the same write, and a counter that reaches the graph's declared cap SHALL trigger the in-place advisor consultation (not an edge); advice SHALL NOT reset the counter

### Requirement: Declared fields are materialized by the write gate

The merged type catalogs plus the tasks' `produces` declarations are the single registry; no separate template file, no materialized registry on disk, and no hand-added fields SHALL exist. The write gate SHALL derive each unit's concrete schema in memory at load: at creation the unit holds the core contract only, and the gate materializes each field with its catalog default at the moment its applicability becomes true — when a node whose pipeline references the producing task is first dispatched (for the phase field: when the phase-approval task records it). Before that moment the field is absent; after it, present with its catalog shape; outside its applicability, always invalid. A unit therefore can never lack a field its route needs nor carry one it does not. Phase values come only from the instantiated `phase` type — no phase is invented at run time.

#### Scenario: Field materialized on first dispatch
- **WHEN** the orchestrator first dispatches a node whose pipeline references a task producing a graph-declared field
- **THEN** the write gate SHALL materialize that field with its catalog default in the same write

#### Scenario: No registry artifact
- **WHEN** the per-unit schema is needed
- **THEN** it SHALL be derived in memory from the merged catalogs and the graph's `produces` declarations, and no generated schema or registry file SHALL be stored as a second source of truth
