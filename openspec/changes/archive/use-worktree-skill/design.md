## Context

WOR-33 defines skills as capabilities mounted on a node, not nodes. Build is mounted with `use-worktree`; Wrap owns cleanup (`graph-node-wrap`: "Wrap cleans residue"). The skill splits into policy (the page) and mechanics (a script): the page states when, how often, what name, and who cleans up, while `skills/use-worktree/scripts/worktree.mjs` performs the worktree operations. The work-unit folder (`graph-plugin-work-unit-state`) gives each stage a directory written by its actor, and only the orchestrator writes `state.json`.

## Goals / Non-Goals

**Goals:**
- Fix what the skill page must state (policy): when to open, how often, what to name it, what Build leaves behind, who removes it, how the script is resolved and what happens when it fails.
- Fix the script's contract (mechanics) for both consumers, Build and codewalk detach mode.
- Stay consistent with the Build and Wrap node specs and the work-unit state layout.

**Non-Goals:**
- Depending on any Claude Code-specific mechanism (native worktree isolation, `EnterWorktree`, sandbox).
- Implementing the script, writing the skill page, rewriting `skills/codewalk/`, or updating docs and README; those are later changes and work units.
- Windows support (explicitly unverified).
- Adding fields to the `state.json` schema.

## Decisions

- **One worktree per work unit, reused across tickets.** Build implements tickets one at a time, sequentially, and later tickets build on earlier ones. A per-ticket worktree would need each ticket's result merged into the next, adding VCS choreography that the orchestrator, not the skill, owns. A single worktree also gives Wrap exactly one thing to remove and keeps the PR a single line of work. Alternative: one worktree per ticket; rejected for the integration overhead and for multiplying cleanup targets.
- **Open lazily at the first Build entry; reuse a live worktree, reopen after Wrap.** Build is re-entered after Review failure, Advisor guidance, or CI red. Wrap removes the worktree before opening the PR and runs CI afterwards, so on CI red the recorded worktree is gone while branch `wu/<id>` still carries the work. Rule: a live recorded worktree is reused; a record naming a missing worktree means Build opens a fresh worktree on the existing branch and rewrites `build/worktree.md`. A work unit that never reaches Build never opens one. Alternatives: open at Trigger, rejected because research-only and no-op units would leave residue; a new branch on CI red, rejected because it would orphan the PR's branch.
- **One identifier: the branch name `wu/<id>`, and the worktree is named by it.** The branch is defined first as `wu/<work-unit-id>` (`id` matches `^[a-z0-9][a-z0-9-]*$`), and the worktree takes that name verbatim, so its path ends in `wu/<id>` (the script resolves the exact path under the path rule below). The name is deterministic, unique per unit, valid for paths and refs, and traceable back to the folder. Ticket ids are deliberately not in the name because the worktree spans tickets. Rationale: one derivation rule instead of two, no mapping between a worktree name and a branch name, and the `wu/` path prefix naturally groups all graph worktrees in one directory. Superseded alternative: a two-name scheme (worktree `<id>`, branch `wu/<id>`), replaced because it needed two rules and a mapping between them. Other alternatives: include the ticket id (contradicts the per-unit cadence); random or timestamp names (not reconstructable by Wrap or a human).
- **Record the location in a Build stage artifact, not in `state.json`.** Build writes `build/worktree.md` in its stage directory, which the work-unit state spec already allows the implementor to write. Adding a `state.json` field would change a schema owned by another change, and the schema forbids unknown top-level fields. Wrap reads it as part of "the worktree and temporary artifacts" it already takes as input. Alternative: orchestrator transcribes the path into `state.json`; rejected as a cross-change schema edit for a value only Wrap needs.
- **Wrap removes; the skill and Build never do.** This follows `graph-node-wrap` directly; Wrap removes the worktree, not the branch. Build's failure paths (blocked, retry) therefore leave the worktree in place, so Advisor guidance and Build retries can still use it. If Wrap cannot find or remove the worktree it reports blocked like any Wrap failure.
- **Script owns dangerous mechanics; pages own policy (supersedes the earlier "self-managed plain git" decision).** Design ruling (owner, Linear WOR-37, 2026-10-01): the earlier decision was a self-contained page of plain `git worktree` commands with no supporting scripts. It is reversed. Criterion: script what agents misexecute destructively or silently (stale-registration recovery, collision handling, path resolution, copy validation); keep prose for judgment. The script is `skills/use-worktree/scripts/worktree.mjs`, zero third-party dependencies, Node.js >= 20 with a startup check, run as `node "<path>"`, with cwd in the consumer project and `GIT_TERMINAL_PROMPT=0`. It has three subcommands: `ensure --branch wu/<id>` (Build), `ensure --detach <sha>` (codewalk), and `setup --worktree <path>` (Build). Output is one stdout JSON object plus distinct exit codes per failure class; diagnostics go to stderr. Rejected alternatives: pure prose (the failure modes above recur; no testable behavior); bash (poor portability and quoting, hard to test, no structured output); a bundled package or shared library (installation and cache-write concerns, cross-skill coupling); third-party dependencies (the plugin cache has no install step). The implementation change verifies the script with committed `node --test` tests.
- **Branch mode and detach mode intentionally resolve the main checkout differently.** Branch mode uses `git rev-parse --git-common-dir` (parent directory), because Build's worktree is a project-level artifact that must be the same regardless of which linked worktree the command runs from; `--show-toplevel` would return the linked worktree itself. Detach mode uses `--show-toplevel`, because the codewalk worktree must stay inside the checkout being read, including a linked one; this preserves `skills/codewalk/SKILL.md` Step 2.
- **Deterministic branch-mode path: `<parent-of-main-checkout>/<main-checkout-basename>.worktrees/wu/<id>`.** The earlier `../wu/<id>` was ambiguous (relative to which directory) and collided across projects sharing a parent. A sibling directory named after the main checkout is unique per project and never nests inside the main checkout, so it needs no ignore-file entry.
- **Stale recovery in branch mode only when the registered directory is absent.** Detach worktrees are disposable and the codewalk oracle force-removes an exact stale path. A Build worktree may hold uncommitted work, so an existing directory is a collision or stale-with-directory-present failure, never removed, never `--force`d. Global `git worktree prune` is never run.
- **No `remove` subcommand, deliberately.** Cleanup is Wrap's (and the user's for codewalk). A scripted remove would hand a destructive operation to actors that must not own it. The only removals are the exact-path stale-registration recoveries.
- **The orchestrator runs the script, not the Build actor.** The implementor rule is that the dispatched actor performs no VCS operations (`agents/implementor.md`), and `graph-node-build` has Build write only code in the worktree. Resolution: the orchestrator runs `ensure` and `setup` before dispatch (first entry and every CI-red reopen) and passes the path; the Build actor never runs `git worktree`, branch, or script commands and reports blocked if given no usable path. Alternative: define provisioning as outside the no-VCS rule and let the actor run the script; rejected because it weakens a bright-line rule that the implementor and reviewer rely on.
- **Script resolution and failure.** The page resolves the script as `${CLAUDE_PLUGIN_ROOT}/skills/use-worktree/scripts/worktree.mjs` when available, else an absolute path passed by the orchestrator (agent-agnostic fallback). On script failure or unavailability the Build stage records blocked and nobody improvises raw `git worktree` commands, which would reintroduce the failure modes the script exists to remove.
- **Rejected alternative: Claude Code native worktree isolation (agent worktree isolation / `EnterWorktree`).** Rationale (design ruling, Linear WOR-37, 2026-10-01):
  - (a) The spec's own requirements are only implementable with self-managed worktrees (script-driven or plain git). Deterministic naming is harness-controlled under the native mechanism, not chosen by the skill; native auto-cleanup of unchanged worktrees contradicts "only Wrap removes"; the CI-red reopen needs separate control of the branch lifecycle and the worktree lifecycle.
  - (b) Portability. Build is a dispatched actor; a Claude Code-only mechanism would lock the vendor into the node spec, whereas a Node script plus git supports other agents (for example codex).
  - (c) Stability. Native behavior depends on settings, sandbox, and version and is not contract-stable; in practice the sandbox has interfered enough to be disabled.
  - Accepted trade-off: there is no runtime isolation enforcement (the script does not sandbox writes). "Write only inside the worktree" becomes contractual and reviewer-verified, consistent with the existing contractual-restriction-over-mechanical-whitelist ruling in `openspec/changes/graph-plugin-architecture/design.md`.

- **Worktree setup is declared config, executed by the script's `setup` subcommand after every `ensure` that creates or reopens a worktree.** A fresh worktree has tracked files only, so dependencies, env files, and large untracked assets are absent. Init investigates the needs and records them in `.harness/worktree-setup.json` (decision in `graph-engineering-node-specs` design.md); The script reads it from the main checkout (the file may not be committed, so the new worktree is not a reliable source), validates it (unknown keys, absolute or `..` copy paths, and missing sources are rejected), and never modifies it. Detach mode structurally never runs setup, preserving codewalk's rule never to execute project code. The orchestrator runs setup on first open and on every CI-red reopen, since each is a fresh worktree. This declared config is the portable equivalent of Claude Code's native worktree setting, which is not used because the native mechanism was rejected (see the "Rejected alternative: Claude Code native worktree isolation" entry above).
  - **Regenerate over copy is the default posture.** Setup commands rebuild dependencies; package-manager caches are machine-level anyway, so regeneration is cheap and stays correct. Copying is reserved for assets that cannot be cheaply regenerated (large data, env files).
  - **Copy-on-write preferred.** `cp -c` (APFS) or `cp --reflink=auto` shares storage until a file diverges, so large assets cost little disk and time yet remain independent per worktree; plain copy is the fallback.
  - **No mutable symlinks.** A symlinked mutable directory would let one worktree's writes alter another's, breaching isolation; symlinks are allowed only for entries the config marks `readonly`.
  - Rejected: symlinking everything (isolation breach); mandatory copy of dependency directories (slow, large, stale-prone).

## Risks / Trade-offs

- [Reused worktree accumulates state from failed attempts; a CI-red reopen starts clean from the branch] -> Review runs against the ticket's verification command, so stale state surfaces as a failing check; Build may discard its own uncommitted changes inside the worktree but never removes the worktree.
- [Name collision if a work-unit id is reused] -> Ids are unique per the state spec; if the computed path already exists and is not a worktree on `wu/<id>`, the script fails with a collision and Build reports blocked instead of overwriting. A record naming a missing worktree with the branch present is the CI-red case, not a collision.
- [Path recorded in a markdown file, not machine-validated] -> Acceptable because only Wrap reads it; a later change can move it into state if more consumers appear.
- [Script becomes a single point of failure for Build] -> Failures are explicit (JSON plus exit code) and surface as Build blocked; the script is covered by committed `node --test` tests in the implementation change. Requires Node.js >= 20, stated as a page prerequisite.
- [Behavior drift between the script's detach mode and codewalk's prose] -> The current codewalk Step 2 prose is the oracle until the codewalk rewrite change lands; that change replaces the prose with a script call.
