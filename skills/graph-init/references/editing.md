# Editing reference

Load at Tier 3. The definition is project-owned reviewable data, generated by `assemble`. Behavior changes by re-assembling it; no agent definition is touched, `.harness/graph.json` is never hand-edited, and the change takes effect through dispatch construction at the next dispatch.

## Procedure

1. Read the current definition, the config, and the project types (`.harness/types.json`).
2. Copy `.harness/graph.json` to a scratch file outside the repo and add `"slots": {}`. The flattened file is then a valid assembly: every node inline, every task in `tasks`. Re-assembling it unchanged reproduces the file byte for byte, so the diff of the re-assembly is exactly your edit.
3. Make the smallest edit that does what the user asked in the scratch file; show the diff and confirm it. A change the user did not ask for is not made.
4. If the edit needs a new or changed type, confirm it and write it first with `types.mjs write --from <draft.json>` (entry rules: `references/templates.md`, Type extensions).
5. Write `{}` to a slots file and run `node "${CLAUDE_PLUGIN_ROOT}/scripts/graph.mjs" assemble <scratch assembly> --slots <empty slots file>`. Assemble validates in memory and writes nothing on rejection: fix the scratch file and re-run; if the user's intent cannot be satisfied within the invariants, explain which invariant blocks it.
6. Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/graph.mjs" validate .harness/graph.json --config .harness/config.json`. Accept only on `"accepted": true`.
7. If the edit changes any walk (a node, a pipeline, an edge, or a phase route), update `.harness/graph.examples.md` to match. The validator never reads it.

A library task that carries `{{slot}}` placeholders (for example `{{test_command}}`) and is not yet in the scratch `tasks` is resolved from the library at assembly, so its slots must be declared in the scratch `slots` (copy name and description from `graphs/coding-factory.json`) and valued in the slots file with the values already confirmed; otherwise assemble rejects with `SLOT_UNDECLARED`. Leave `phase_values` undeclared: the phase vocabulary changes through `types.mjs write`, not through re-assembly.

## Common edits

| Edit | Rule |
|---|---|
| Change a command | Edit it in the scratch file wherever a task declares it: `equipment.commands` entries (including the `family` of state-sourced entries) and `run` lines. A slot value is already filled in the flattened file, so replace every occurrence; a family stays base program plus leading arguments. The tool gate re-probes it |
| Swap a task in a pipeline | Change the entry's `use` to another catalog task (or a library task id), bind its params in `with`, and map every exit outcome of the new task in `on`: `next`, `goto:<earlier task>`, a surfaced node outcome, or `escalate`. A task appears at most once per pipeline |
| Rebind a param | Edit the entry's `with`; it binds exactly the params the task declares |
| Add or remove an edge or guard | Edit `edges`. Each surfaced outcome keeps edges whose guards are mutually exclusive and jointly exhaustive over the phase values that reach the node; the entry node keeps its one unconditional edge; no edge leaves a terminal or enters the entry node |
| Add a human approval task to a pipeline | Add a TaskDef with executor `human`, an exit `artifact` recording the decision, and its outcomes (for example `approved`, `send-back`, `not-needed`); reference it from the pipeline and map every outcome in `on` (`send-back` to `goto:<earlier authoring task>`; a `not-needed` that abandons surfaces as a node outcome with an edge to the abandonment terminal). The phase approval stays the only producer of `phase`, at the shared first node |
| Wrap an external skill | Author one TaskDef: the skill under `equipment.skills` (a profile-bearing skill must be installed), its `reads`, `produces`, `restrictions`, and `exit`; reference it from a pipeline. Each new state field it produces is a confirmed type extension, written with `types.mjs write` before the re-assembly |
| Add or change a phase value | Write a new instantiated `phase` entry through `types.mjs write` (`maintenance` stays in it), and edit the edges that route the value: every phase value needs a route to the success terminal |
| Add a node | Declare the node (`id`, `kind`, `purpose`, `pipeline`, `outcomes`), cover every surfaced outcome with edges, and keep it reachable with a route to the success terminal; never add advisor, blocked, or escalation nodes or edges |
| Add a loop | Needs an exit and the declared caps (a `goto` needs the failure cap, a cycle the edge-revisit cap) |
| Change caps | Positive integers; `edge_revisit` and `advisor_consultations` bound the in-place fallback chain |

## Config edits

Config changes (locations, worktree setup, memory thresholds, the `graph` path) are bootstrap work: draft the full new config and write it through `init.mjs write`. Never edit `.harness/config.json` by hand.

## In-flight units

A definition or type change applies to later dispatches. A unit's recorded state is checked against the graph and the catalogs, so a change can invalidate a unit that is mid-run: a removed node or task on its walked path or at its pipeline position, a phase value no longer in the catalog, a field whose type changed. Recommend finishing or abandoning live units before a structural or type change, name the units affected, and write the type and re-assemble in one session: a type change (a new phase value, for example) can make the current `.harness/graph.json` fail validation until the re-assembly lands, so end with the full validation.
